# 第1事件の演出メモ

## 方針

プレイヤーは調査員本人。画面下の「調査員・心の声」に、括弧付きの短い内心を表示する。捜査端末に向き合う静かな始まりから、資料を読み、自分で判断し、報告をまとめるまでを一人称でつなぐ。口調は落ち着いた自然な日本語にそろえ、緊張と小さな手応えを添える。

物語の中心はプレイヤーがIP、設定、ログを読む時間。内心は資料の意味を代わりに推理する語り手にしない。新しい人物、出来事、障害、観測事実は加えない。真因、証拠、反証、採点、重大な危険操作、解決条件は `docs/GAME_DESIGN.md` と `src/data/case01.json` のまま扱う。

## 視覚方針・タイトル画面

黒とチャコールの現代的な捜査端末を基調にする。背景は `#090C10`、資料面は `#141A22`、本文は `#EDF2F7`、補助文字は `#A7B3C2`。シアン `#72D9EC` は選択中のタブ、細い区切り、主要操作の輪郭に絞る。丸みは小さく、余白と細い罫線で情報を整理する。緑・クリーム色、かわいい机や文具のイラストは使わない。

専用タイトル画面では「通信捜査室」を大きく置き、その下に短いコピー「記録を読み、真相をつなぐ。」を添える。背景は暗い端末の反射とごく淡い配線の影を使い、タイトル周辺に静かな空間を残す。実際のIP、ログ、設定、警告などの読める情報を背景に描き込まない。主役はタイトルと開始操作。背景の端に細いシアンの光を置き、静止した画面でも緊張感を出す。

調査画面の資料は白い文字を持つ暗いパネルで、見出しと本文を明確に分ける。ログとIPは読みやすい等幅表示を維持する。正解へ導くような赤い強調、派手な発光、点滅、擬似アラートは加えない。下部の心の声は、チャコールの吹き出しに小さな「調査員・心の声」ラベルと本文を置く。外周の細い線と小さな切り欠きで会話欄と分かる形にし、人物の顔や立ち絵は追加しない。

画面を切り替えた瞬間に短い内心が更新され、資料を読む時間へ戻る。演出は短いフェード程度に抑える。タイマー、強制的な会話送り、乱れた画面による読みにくさを足さず、読み解く行為そのものに緊張感を持たせる。

## 量と表示タイミング

`src/data/narrative.json` に、調査室・依頼・開始の3行、4タブの4行、8証拠の8行、提出前の1行、結果の2行、再挑戦の1行を収録する。計19行。各行は括弧を含め原則40〜65文字。依頼本文は200〜350文字で、正本の依頼内容と正常要件だけを再構成する。

タブや証拠をタップしたときに、その画面に対応する内心を1行表示する。必須の長いカットシーン、複数段の会話送り、強制待機は作らない。同じ場所を開いても文言は変えず、閲覧順や仮説の分類を物語の分岐に使わない。内心を表示したまま資料を読めるようにし、ゲーム操作やログの閲覧を妨げない。

`tabs.report` は報告タブを開く瞬間、`reportThought` は提出前の確認に使う。`resultThoughts` は採点済みの状態に対応させるが、成功の文言で実際に修復を実施した、新しいログを得た、といった事実を追加しない。`retryThought` は新しい試行の開始時に使う。

## UIでネタバレを避ける

心の声は、資料を読むときの気持ちや自分の読み方を述べる。特定の仮説の正誤、証拠の重要度、ノイズ、矛盾、原因の機器、具体的な比較対象は述べない。証拠ごとの内心にも作者用の役割や正答IDを渡さない。アラートの内心は警告を見たときの緊張にとどめ、その資料が事件と関係するかを判定しない。

途中の仮説分類や根拠の関連付けには、正誤を示す色・音・台詞を付けない。明示的に開く既存の3段階ヒントと、提出後の解説は別の機能として扱う。用語辞典には一般的な定義を置き、この事件の症状に特化した答えを加えない。

ユーザー向けの制作報告やプレビューでは、答え、正しい根拠の組み合わせ、証拠の作者用役割を明かさない。

## 採用した全セリフ

### 調査室・依頼・開始

- `roomThought`：（机に向かうと、少しだけ気持ちが落ち着く。今日の調査も、私の目で読んだ記録から始めよう。）
- `requestThought`：（依頼を読むたび、向こうで待つ人のことを考える。焦る気持ちはあるけれど、まずは状況を受け止めよう。）
- `startThought`：（よし、調査を始めよう。気になる資料から開いて、分かったことは私の言葉で整理していけばいい。）

### タブ

- `tabs.topology`：（構成図が目の前に広がった。機器の名前とアドレスを確かめながら、頭の中にもこの図を置いておこう。）
- `tabs.evidence`：（資料はここにそろっている。一枚ずつ読んで、気になるものは手元に残そう。結論を急ぐ必要はない。）
- `tabs.hypotheses`：（頭の中の考えを、ここに並べてみよう。今は保留のままでもいい。確かめるたびに、私の判断を更新しよう。）
- `tabs.report`：（調査の記録を報告にまとめる時間だ。選んだ言葉と根拠を見直して、今の私が説明できる形にしていこう。）

### 証拠

- `evidenceThoughts.E01`：（現場の報告を読むと、画面の向こうの困りごとが伝わってくる。まずは書かれていることを、丁寧に受け取ろう。）
- `evidenceThoughts.E02`：（問い合わせの記録が開いた。短い行にも数字が並ぶ。見慣れた言葉だけで読み流さず、内容を追ってみよう。）
- `evidenceThoughts.E03`：（診断の結果が並んでいる。一度に頭へ入れようとすると混ざりそうだ。私は一行ずつ、確かめながら読もう。）
- `evidenceThoughts.E04`：（ログを開いた。記録の一行一行に、実際の通信が残っている。読み取った内容と、私の考えを分けておこう。）
- `evidenceThoughts.E05`：（設定表を読む時間だ。細かい数字が続くけれど、ここは落ち着いて読める。分からない用語は確かめながら進もう。）
- `evidenceThoughts.E06`：（作業記録には、行われたことが言葉で残っている。知っているつもりで先を読まず、記載を最後まで確かめよう。）
- `evidenceThoughts.E07`：（確認結果と記録が開いた。何を確かめた資料なのか、私の中で整理しておこう。そこから先は、自分で考える。）
- `evidenceThoughts.E08`：（アラートの記録を開いた。警告という言葉を見ると少し身構える。ひと息ついて、書かれた内容を読んでいこう。）

### 提出前・結果・再挑戦

- `reportThought`：（提出する前に、もう一度だけ読み返そう。選んだ内容を自分で説明できるか。私の調査は、ここまでの記録にある。）
- `resultThoughts.solved`：（報告をまとめられた。少し肩の力が抜ける。たどった考え方を振り返って、今日の調査を自分の経験にしておこう。）
- `resultThoughts.reconsider`：（まだ納得できるところまで届かなかった。でも、読んだ記録は残っている。私がどう考えたのか、振り返ってみよう。）
- `retryThought`：（もう一度、この依頼に向き合おう。前に選んだ答えを追うだけでなく、私自身の目で記録を読み直してみたい。）

### 依頼本文

貸出機材を管理する事業所から、調査の依頼が届いた。座席移動のあと、営業チームだけが申請Webを開けなくなっている。ブラウザは待ち続け、最後にはタイムアウトしてしまう。一方で、運用チームは同じWebを利用できている。

依頼は、この状況を生んでいる原因を特定し、必要な通信だけを復旧させること。正常時には、営業と運用の両チームが https://request.example.test のTCP/443へ接続できなければならない。未承認の端末や他のポートまで許可してはいけない。使える状態と、守るべき通信の条件。その両方を満たす調査報告をまとめよう。
