## 任意提案

### O1：スマホ概要図の表示仕様を作者欄で揃える

全稿とも縦軸・枝・線種・観測点を指定し、故障箇所を色で教えない点は適切。NET04のA/B列を交差させない指示、NET05のキューを機器内枠にする指示は特に有効。実装前に「360px概要では機器名・役割・業務方向・境界だけ、全IP/プレフィックス/IF/観測点は既存の詳細表示」の密度ルールを5稿共通にするとよい。NET03のpublic client/RP/DNSには外部区間を抽象化した注記、内部側には/24を明記し、未記載の外部prefixを推測で埋めない。

### O2：内心の役割を少し変化させる

内心は正解IDや読むべきEIDを教えておらず、会話で証拠の解禁もしていない。ただし5稿とも「私は範囲/条件を読もう」「結論を急がず」と似た注意が続き、業務の切迫感が薄くなる。数字の読み方を繰り返す内心の一部を、待つ来館者、段取り、積み込み、通訳者へ渡す説明に戻す短い心情へ置き換えると、同じゲーム手順でも事件ごとの手触りが出る。技術値や推理のヒントは加えない。

### O3：NET05のパケット数・帯域・用語の粒度

E03の10秒/1000 RTP packetが音声2Mbit/sの全数なら、平均IP長は2,500 byteとなる。通常MTUを勝手に仮定して矛盾と断定はしないが、全数なのか照合用抽出1000件なのかは明記した方がよい。抽出なら抽出条件と「対象抽出の欠落0」を示し、全1分の計測へ外挿しない。全数ならIP長とMTU/非断片化条件を整合させる。新しいPMTUD障害を追加しない。

主担当からの最小案「1秒/1000 packet」なら、IP総長250 byte・1000ppsで2Mbit/sとなり、MTU1500の非断片化で整合する。観測範囲を10:04:00–10:04:01とし、observedAtは終端以後、seq1200–2199の対象全数、IP総長250byte、IP/UDP/RTPを含む計測値を明記すれば、同じパケットの境界前後を比較する目的を保てる。1分の品質計測そのものをこの1秒へ短縮する必要はない。

「Gi2は0に整形」はDSCP書換とレートshapingを混同しやすいので「DSCP0へ書換」に統一すると読みやすい。辞典ECNの「IPヘッダの下位2ビット」は「IPヘッダのDSフィールド下位2ビット」へ精密化する。受信間隔変動をRFC jitterと区別する現方針は維持する。
