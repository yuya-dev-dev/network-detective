# 第1事件MVPの実装記録

作者・開発者向け。採点の構造を含むため、プレイヤーへの制作報告に解答を転記しない。

## 最小構成

```text
src/
  data/        case01.json（事件）・narrative.json（一人称の演出）
  scenario/    型・実行時検証・プレイヤー用データの投影
  game/        報告型・純粋な採点関数・reducer
  storage/     localStorageの読込検証・保存
  app/         Provider・画面遷移・保存と採点の接続
  ui/          構成図・証拠・仮説・報告・結果・共通部品
  pwa/         登録・更新通知・Service Workerテンプレート
  main.tsx
  styles.css
public/
  art/         圧縮したタイトルイラスト
  icons/       PWAアイコン
  manifest.webmanifest
scripts/
  validate-scenario.ts
  build-sw.mjs
  prepare-art.mjs
tests/
  unit/        採点・状態・シナリオ・保存
  e2e/         UI通しプレイ・PWA
  helpers/     報告fixture・操作・実ビルドの配信サーバー
```

React＋TypeScript＋Vite、通常CSS、SVG、JSON、reducerで実装した。バックエンド、追加事件、大きな状態管理ライブラリは導入していない。

## 責務の分離

`case01.json` は第1事件の事実、選択肢、作者用解答を保持する。ビルド前に必須項目、IDの一意性・参照、採点集合、ログ・表の構造を検証する。`load.ts` から調査UIへ渡す投影には `solution` を含めない。解答の暗号化やクライアント内の秘匿は要件外。

`scoring.ts` は報告と作者用解答を入力とする純粋関数。成立集合はOR/AND、矛盾は0点を優先、部分点は5点、成立は10点。順序・重複は正規化する。解決条件とcriticalは仕様の条件をそのまま評価し、隠れ減点を付けない。必須証拠と無関係証拠を併記した場合の扱いはユーザー承認済みの解釈をテストで固定した。

`reducer.ts` は依頼・調査中・提出済み・完了の段階、閲覧・ピン留め、仮説と証拠の関連付け、ヒント、下書き、結果記録を扱う。提出は試行ごとに1回。再挑戦は新しいIDを作り、過去記録を残す。

`localStorage.ts` は保存の構造を検証する。同じrevisionの結果は報告から再計算する。破損時は新規開始へ案内し、revision違いの途中試行は適用しない。事件ごとに保存キーを分ける。`GameProvider` は操作を順番に保存し、Web Locksと最新保存の照合で同じ試行の同時提出を調停する。保存失敗時は通知してメモリ上で続行する。

UIは採点せず、表示と操作を担当する。画面遷移はhashで管理し、ブラウザの戻る操作に対応する。専用タイトル→一覧→依頼→調査→結果へ進む。タイトルへ戻っても試行を初期化しない。4タブを保持して展開状態を残し、タブごとのスクロール位置を復元する。主人公の心の声は別の演出JSONから読む。黒・チャコール・白を基調に、控えめなシアンで選択状態を示す。

Service Workerはビルド資産全体のハッシュをキャッシュ世代に使う。事件JSONもアプリへ同梱されるため世代を混在させない。取得完了後はキャッシュから起動する。更新は一覧で保存成功後に適用し、他タブがある場合は停止する。

## 実装したタスクの順序

1. 第1事件JSON、データ型、参照検証を作る。
2. 採点を実装し、正答・部分点・別の有効集合・無関係証拠・矛盾・危険操作を固定する。
3. reducerと保存を実装し、提出1回、再挑戦、破損・revision違いを確認する。
4. タイトル→一覧→依頼→調査→報告→結果を接続する。
5. SVG構成図、全8証拠、固定診断、ログ表示切替を作る。
6. 仮説分類と支持・反証の関連付け、ヒント、辞典を作る。
7. 結果の個別解説と証拠への戻り、初回・最新記録を作る。
8. 作家の一人称演出と生成イラストを組み込み、スマホ表示を確認する。
9. PWA、オフライン、保存後の更新を実装する。
10. 田中の独立レビューを受け、保存競合、タブ保持、図中文字の見切れを修正する。
11. 全検証を実行し、Gitの1つのPRへまとめる。

## 設計書の曖昧さと実装判断

採点の補助証拠と無関係証拠の併記、正常要件の未承認端末の範囲は解釈の余地があった。具体的な採用理由は `REVIEW.md` に記録した。ユーザーはプレイヤーであるため、解答に関わる確認を再度求めず、証拠・真因・修復を維持する最小限のcontext補完を行った。

固定時刻の日付は2026-09-30 JSTとした。過去の記録を比較する証拠の時刻は、障害スナップショットより前のまま保持する。結果は修復計画の評価であり、変更後の新しい診断や設定シミュレーションを追加していない。

## 検証範囲

最終実行結果は `REVIEW.md` の検証証跡へ記録する。必須資産のgzip合計はビルドで計算し、1MBを超えると失敗する。この値はローカルの圧縮計算であり、実配信の転送量ではない。

自動化した範囲：正答100点、原因だけでは未解決、危険操作では未解決、採点の各境界、全証拠の任意順閲覧、下書きと閲覧状態の再読込、タブの展開・スクロール保持、解説から証拠への戻り、壊れた保存と保存不能、複数タブの同時提出、360/390/430pxの横はみ出し、オフライン通しプレイ、世代更新と保存保護。

WebKitのオフライン模擬フラグに既知の制約があるため、WebKitでは実配信サーバーを停止する。未キャッシュcontextの接続失敗を対照に、キャッシュ済みページがService Worker経由で再読込・通しプレイできることを確認する。

## 実機で残る完成条件

この環境では物理的なiPhone・Androidを操作していない。ブラウザエンジンの自動テストを実機確認済みとは扱わない。設計書の完成条件のうち、次は未検証。

- iPhone SafariとAndroid Chromeで、一覧から結果まで全操作を行う。
- OSの戻る、再読み込み、キーボード・セーフエリアを含む実際の表示を確認する。
- キャッシュ完了後、機内モードで再起動して通しプレイする。
- HTTPSの実配信で初回必須取得の転送量を測る。

実施時は端末名・OS・ブラウザのバージョン・配信URL・結果を追記する。未確認の実機ゲートを完了扱いにしない。
