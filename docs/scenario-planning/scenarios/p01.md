# P01 切り替えたはずの夜

**作者用完成稿・ネタバレあり。** 前半はプレイヤーに提示できる依頼・台詞・資料、後半は作者専用の真相・採点。企画段階の文章であり、実装・公開順・事件番号を確定しない。

## プレイヤー向け：依頼と導入

### 依頼

上映に使う字幕を、二つの班が今夜のうちに仕上げています。保存サーバの切替後、先に作業を始めていたA班だけが保存できなくなりました。後から入ったB班は保存できており、A班の画面にはまだ未保存の文章が残っています。作業をやり直す時間はありません。両班の通信と保存の記録を調べ、影響範囲と原因を報告してください。復旧では、残っている編集を失わず、新しい側で保存を確認してから旧側を止める必要があります。新旧は同じ素材ストアを使っています。正常な班の保存も続けられる、安全な移行手順と確認計画をお願いします。

### 人物と声

- 志保：字幕制作の取りまとめ。言葉を一つずつ大切にする。「消したくない」「この行まで」と具体的に話す。
- 蓮：切替担当。簡潔な記録口調。実施したことと、確認できていないことを分ける。
- 調査員：プレイヤー本人。一人称の内心だけを画面下に出す。

### 正常要件・構成

既存班の未保存内容を失わず新側へ移行し、両班が保存できること。旧保存受付は再開しない。切替前後のサーバは同じ権威素材ストアを参照する。

```text
端末A 10.61.1.23 / 端末B 10.61.1.24
DNS 10.61.10.53
caption.example.test → 旧10.61.20.11 / 新10.61.20.12
旧・新 → 共通素材ストア10.61.30.18
保存通信：TLS / WebSocket / TCP443
```

全9資料は開始時から一覧にあり、任意順に開ける。日付は2026-10-01/JST、時計誤差100ms以内。20:10固定のスナップショットで、取得順で結果は変わらない。

### E03 保存アプリの運用仕様〔資料・事前有効〕

ログイン時にwssのTCP443接続を作り、そのconnection IDを保存にも使う。接続中の名前再解決と自動再接続は行わない。この仕様は本アプリのものである。

新規接続は新IPのみへ向かい、旧側は20:00以降の新規接続を拒否する。既存WebSocketの受信・応答と保存受付は別機能。保存受付停止でも端末のドラフトは消えず、書出しできる。

新旧の参照先は共通ストア10.61.30.18。ドラフトには編集IDと基底revisionが付く。新側でストアを読み直し、履歴・一意編集ID・基底revisionを照合して取り込む。重複又は古い上書きは拒否する。対象D11とD12は別の編集対象で、D11の同時編集者はいない。

内心：（文章を渡す仕組みにも、守るための順序がある。まだ画面に残る一行のために、停止時の約束も読んでおこう。）

### E06 承認条件と実施記録〔資料・20:03〕

承認条件：未保存内容の保全、新側への保存確認、既存接続と未保存の残数確認後に旧側を停止。

実施欄：20:00 DNS変更 → TTL経過 → 20:03旧側の保存受付停止。既存接続数とドラフト確認の記入欄は設けられていない。保存受付フラグだけを操作し、旧ノードの電源停止はしていない。

内心：（作業を終えた人にも、待っている人にも理由がある。責める言葉を先に書かず、実施と約束をそれぞれ読もう。）

### E07 新側の保存試験〔診断・20:06〕

正規URLでTLS検証有効、healthは200。U11の編集権限は変更されていない。新接続による試験文書の保存成功を確認。共通ストアの読み書きと、新旧が同じストアを参照する状態は正常。この試験文書はA班D11のドラフトではない。

内心：（保存できたという言葉は、待っていた人には嬉しい。私も一息つきたいけれど、試した対象まで読んでおこう。）

### E08 残されたドラフトと移行手順〔資料・20:06〕

```text
Aローカル：D11 / edit K11 / 基底rev7 / 未保存ドラフトあり
ストア：D11 rev7 / 保存済み内容と保全ハッシュ一致
D11の他編集者：0
```

承認済み操作は、ドラフト書出しと整合確認 → 新接続 → 基底revision・履歴・編集ID照合 → 取込み → コミットとハッシュ確認 → 旧接続終了。旧側の保存受付を再開せず、共通ストアへ移す。この資料は可能な手順を示すもので、復旧を実行済みとする結果ではない。

内心：（残った文章にも、受け渡しに使える札が付いている。取り戻したい気持ちは強いけれど、操作の順序を急がず読もう。）

## 採点後に表示する解説

A班の保存が失敗する一方、B班は成功し、A班の画面には未保存内容が残っています（E01/E08）。両端末の現在の名前解決は正規の新IPです（E02）。しかし保存アプリはログイン時の接続を再利用し、接続中に名前を引き直しません（E03）。Q11は19:55開始の旧向けW11を使い続けています（E04/E05）。新側の停止・TLS不良・権限剥奪では、この記録を説明できません（E04/E07）。

旧側ではW11が残るまま保存受付を停止し、Q11をSAVE_DISABLEDで拒否しています（E05）。移行記録はTTL経過から保存停止へ進み、既存接続とドラフトの確認がなく、未保存を失わず移行する承認条件に一致していません（E06）。現在のDNSが新しいことと、すでにある接続の移行を同じものとして扱った手順が原因です。

記録とドラフトを保全し、共通ストアの基底revision・履歴・一意編集IDを照合する承認手順で、新接続へ引き継ぎます（E03/E08）。旧保存受付を再開する必要はありません。D11の新側コミットとハッシュ、peer新、旧接続0、未保存0、新規班の正常保存を確認してから旧を止めます。この説明は計画であり、復旧を実行済みとする新しいログではありません。
