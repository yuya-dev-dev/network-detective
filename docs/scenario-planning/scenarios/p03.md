# P03 大きな荷物だけ届かない

**作者用完成稿・ネタバレあり。** プレイヤー向け本文と作者向け真相・採点を分ける。提出後解説は採点後だけ表示。企画稿であり実装・公開順は未確定。

## プレイヤー向け：依頼と導入

### 依頼

映像編集の現場で、素材一覧は開くのに、必要な大きい素材を取得できなくなりました。同じ端末から短い確認ファイルは取得でき、画面上では接続も済んでいるように見えます。編集担当は、素材を選び直すべきか、待つべきか判断できずにいます。指定されたVPN経路の通信記録を調べ、成功した段階と止まった段階を区別して報告してください。正常時は大小のHTTPS取得ができ、承認経路が生成するサイズ通知もサーバへ届く必要があります。必要な制限は保ったまま、この要件を満たす恒久修復と再発防止、取得完了まで確かめる計画をお願いします。

### 人物と声

- 奏：映像編集担当。完成の手触りを気にする。「一覧で見る」と「手元で使う」を分け、少し苛立っても人を責めない。
- 南：経路管理担当。慎重で淡々と話す。観測位置と承認条件を明確にする。
- 調査員：プレイヤー本人。下部の内心は初見の記録に対する気持ちを伝える。

### 正常要件・構成

一覧・小素材・大素材をHTTPSで取得できること。承認VPN経路からサーバへ戻るPMTUD通知が通ることも正常要件。IPv4のみ。本調査対象フローにNAT・プロキシ・別経路なし。

```text
編集端末10.63.1.23 → 拠点VPN終端 → 中央VPN入口G10.63.10.1
→ FW VPN側10.63.10.254 / サーバ側10.63.20.1
→ 素材サーバ10.63.20.18:443
素材データはサーバから端末へ逆向きに流れる
```

全11資料は開始時から公開、任意順。2026-10-01/JST、時計誤差100ms以内。14:10固定。診断で設定や障害状態は変わらない。

## プレイヤー向け：全資料本文と内心

### E01 編集席の取得報告〔資料・14:05〕

同じ端末で14:05に一覧と256Bの短い確認ファイルを取得。確認応答はHTTP/TLSを含め、個々のIP全長が1000バイト以下。40MBの素材取得は停止した。ファイルの総量は、通信中の各パケット長とは別の値である。現場の報告として記載し、詳細な通信段階は診断で確認する。

内心：（欲しい素材が分かっているからこそ、待つだけの時間は長い。私は大小という言葉を、まず記録の値に戻そう。）

### E02 接続の段階別記録〔診断・14:06:00〜03〕

```text
14:06:00 正規Aと端末応答：10.63.20.18
14:06:01 TCP三者ハンドシェイク完了
クライアントSYN広告MSS：1460
14:06:02 TLS証明書検証成功
TLSハンドシェイク中の全IPパケット：1380バイト以下
14:06:03 短い確認応答：HTTP200
```

端末とサーバ双方で対応を確認。各成功はその段階の観測で、40MB取得完了の記録ではない。

内心：（成功の印がいくつも並んでいる。安心して最後の行を飛ばさないように、私はどの段階の記録かを見ておこう。）

### E03 承認経路の仕様〔資料・14:06〕

経路は構成欄のとおり。旧経路の上限は1500、現在GからVPNへ転送できる内側IP全長の上限は1380で、承認済みの正常仕様。ホストLANのMTUは1500。サーバ側PMTUの初期値も1500。

サーバはPMTUD有効。ブラックホール回避、自動MSSクランプはない。転送上限を超えるDF付きパケットをGが破棄した場合、type3/code4とnext_hop_mtu1380をサーバへ返し、サーバは通知から送信サイズを縮小する設計。送信データのIPv4ヘッダ20バイト、TCPヘッダ20バイト、データセグメントにオプションなし。SYNのMSSオプションとは区別する。

内心：（道には、通れる荷物の大きさと知らせ方が決まっている。私は承認された条件を読んで、普段の動きを掴もう。）

### E04 サーバ出口の実線上パケット〔診断・14:06〕

```text
14:06:04.000 src10.63.20.18:443 → dst10.63.1.23:51000
TCP seq9001 / IP全長1500 / DF=1 / TCPデータ1460
14:06:05.000 同フロー・seq9001再送
14:06:07.000 同フロー・seq9001再送
```

送信NICで実線上のパケットを捕捉した。オフロードの表示上だけの巨大パケットではない。対象フローと関連ICMPの収録範囲14:06:00〜08、捕捉欠落0。

内心：（繰り返された番号を見ていると、待っていた時間が形になる。私は同じ番号の通信を、途中で取り違えず追いたい。）

### E05 VPN入口Gの転送・通知記録〔診断・14:06〕

```text
14:06:04.010 対象フロー・seq9001：転送上限超過で破棄
14:06:04.011 ICMPを生成・送信
src10.63.10.1 → dst10.63.20.18
type3/code4 / next_hop_mtu1380
引用：src10.63.20.18:443 → dst10.63.1.23:51000 / seq9001
```

簡略記録は引用元の識別キーを表示し、元パケットのIP全長とDFは重複掲載しない。対象フロー・関連ICMPは14:06:00〜08の全記録、欠落0。

内心：（途中の装置からも、時刻付きの記録が届いている。私は大きな流れに飛びつかず、この場所の動作を読み終えよう。）

### E06 FW両側とサーバ受信の記録〔診断・14:06:04.012〜04.020〕

```text
FW VPN側受信：src10.63.10.1 → dst10.63.20.18
ICMP type3/code4 / next_hop_mtu1380
引用：src10.63.20.18:443 → dst10.63.1.23:51000 / seq9001
FW判定：rule10 DROP
FWサーバ側送出：0 / サーバNIC受信：0
```

この区間の全該当通知を収録、欠落0。元パケット全長・DFの表示はなく、引用キーで対応を確認する。前後を含む14:06:00〜08の関連通信の捕捉も完全。

内心：（届かなかったという記録には、見た場所の裏付けがある。私は両側の時刻と対象を揃えて、読んだ範囲を残そう。）

### E07 FWの全規則と変更記録〔資料・14:07〕

```text
この方向の規則：上から最初に一致した1行を適用
rule10 全ICMP DROP
rule20 成立済み通信に関連するICMP ALLOW
rule30 承認TCP443 ALLOW
rule99 その他 DROP
```

この4行はVPN側→サーバ側の新規通信と関連ICMPを評価する全規則。許可済みTCPの戻り通信は状態で許可するが、関連ICMPは上の4行を記載順で評価する。関連ICMPの状態判定機能は有効。14:00にrule10を追加した。PMTUD通知を通す正常要件は変更されていない。

内心：（規則の名前だけでは、実際の順番を見落としそうだ。私は上から読むという約束を守って、設定を一度辿ろう。）

### E08 TCP443の固定サイズ診断〔診断・14:08〕

許可済みTCP443のサーバ→端末応答をDF付きで固定した保存済み試験。IP全長1380は端末受信とACK成功。1381は応答データをGで破棄し、同診断フローを引用するMTU通知をFWでDROPした。値はIP全長であり、Echoのpayload値ではない。ICMP Echoはrule10で拒否されるため試験に使用していない。

内心：（一バイトの差にも、測り方と応答が記録されている。私は数の大小だけを眺めず、何を送った試験か読もう。）

### E09 素材サーバの処理記録〔資料・14:06〜09〕

CPU12%、読出し待ち0。対象素材の読出しは完了し、アプリの拒否なし。指定プロセスの全記録を収録した。これはサーバ内部の処理状態であり、端末への取得完了を直接示すものではない。

内心：（サーバの中で終わった仕事と、編集席で使える仕事がある。私は負荷の数字を読んで、その観測場所も覚えておこう。）

### E10 別承認経路の保存試験〔資料・13:40〕

素材ID F17、同じ版と同じハッシュの40MB素材を、別の承認経路から取得完了した記録。現在調査しているVPN経路の試験ではない。素材本文は公開せず、版とハッシュの一致を表示する。

内心：（使えた記録にも、使った道の情報が添えられている。私は同じ素材という条件と経路の条件を、別々に持っておこう。）

### E11 設備の申し送り〔資料・前日〕

ヘッドホンの接触警告があり、前日の交換で解消。依存先欄では、素材のネットワーク取得・保管処理に接続していない機器と記録されている。

内心：（編集席には、通信以外の道具もたくさんある。警告という言葉に急かされず、日付と対象を見てから考えよう。）

## プレイヤー向け：演出・支援・締め

- 構成：（行きの要求と戻る素材は、同じ図で向きが変わる。私は端末からの目線だけで読まず、矢印を確かめておこう。）
- 証拠：（取得できない時間を、ただ待った時間にしたくない。私は記録された時刻と場所を拾い、読める形に並べていこう。）
- 仮説：（接続済みという一言で説明を閉じるのは早そうだ。私は成功した範囲を守りながら、残った出来事も考えたい。）
- 報告：（素材が手元で使えるところまで、手順は続いている。私は制限を守った修復と、取得完了を確かめる計画を書こう。）
- 提出前：（数字に気を取られて、編集席の目的を落としていないだろうか。私は根拠と確認計画を、使える素材へ向けて整えよう。）

任意ヒント：①成功したのは通信のどの段階か。②サーバ送信記録と転送可能サイズを比較する。③同じ通信を引用する通知が、サーバへ戻る道を追う。通常の内心には表示しない。

辞典：MTU＝一度に転送できるIPパケットの大きさの上限。IP全長＝IPヘッダを含むパケット全体の長さ。DF＝IPv4で途中の分割を禁止する指定。ICMP引用＝通知がどの通信に関するものかを示す元パケットの情報。MSS＝TCPで相手に広告するデータ部分の最大長。PMTUD＝経路の通知から送信サイズを調整する方式。辞典の説明から今回の原因を指示しない。

解決時：奏「一覧を見るだけじゃなく、素材を使うところまでの計画になりましたね」／南「必要な制限を残して、承認された通知の道を戻します」／調査員「取得が終わることと、その内容まで確認しましょう」

内心：（接続済みの表示の先に、まだ確かめる仕事があった。私は編集席まで届くことを、最後の確認から外さずに済んだ。）

再検討時：奏「素材は選び直さずに、いったん待ちます」／南「各観測点の記録は残しています」／調査員「成功した段階と、その先の説明をもう一度繋ぎ直します」

内心：（小さな成功に、少し安心しすぎたかもしれない。私は同じ通信の時刻を読み直し、まだ説明できない所を探そう。）

## 作者専用：真相・全報告候補

単一真因は14:00追加の全ICMP拒否が、関連PMTUD通知にも先に一致したこと。正常な1380のVPN経路を故障としない。E04の1500/DF、E05の破棄と生成、E06の通知遮断、E07の順序が機序を示す。

MSSを1340以下へ調整して新規TCP接続を作る暫定対策は技術的に有効。本稿では「今回の恒久修復」を選ぶ契約で、PMTUD回復を含む。MSSクランプ単独を誤答カードにしない。将来代替カードを作る場合は必要なICMP修正と組み合わせて再レビュー。UDP・他VPN等の未観測障害を足して別解を潰さない。

未確定：他VPN、IPv6、UDP、全素材、今後の動的MTU、通信相手の人間の身元。

## 採点後に表示する解説

14:05の現場確認では一覧と小応答を取得でき、大素材だけが止まりました（E01）。14:06の診断対象フローでも名前解決、TCP、TLSは成功している一方、サーバは1500バイト・DF付きの同じ通信を再送しています（E02/E04）。素材の別経路試験と処理記録は、素材破損や高負荷の説明に合いません（E09/E10）。

1500の通信は正常な上限1380を超えます（E03/E04）。入口Gは破棄してサーバへMTU通知を生成しますが（E05）、同じ通信を引用する通知はFWでDROPされ、サーバ側へ出ていません（E06）。関連通知を許可する規則より全拒否が先にあり、PMTUDを通す要件と一致しないのが原因です（E07）。
