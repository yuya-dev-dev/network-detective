# P07 届いた覚えのない返信

**作者用完成稿・ネタバレあり。** 依頼・台詞・資料はプレイヤー向け、真相・ルーブリックは作者向け。提出後解説は採点後だけ表示する。企画稿であり実装や公開順を決定しない。

## プレイヤー向け：依頼と導入

### 依頼

貸出店のメール窓口に、送った覚えのない失敗通知が次々に届いています。予約係は本来の予約連絡を探すだけで手いっぱいです。店名を表示したメールを受け取ったという申告もありましたが、表示名だけでは送信経路が分かりません。店のサーバで何を受け付け、どこへ引き渡したかを調べてください。正常時は、外部から店への受信を続け、正規の予約通知も送れる必要があります。一方、未認証の外部接続に外部宛ての中継を許してはいけません。保全した受付・配送・認証記録から影響範囲と原因を報告し、必要な連絡を止めずに戻す手順と確認計画をお願いします。

### 人物と声

- まどか：貸出店の予約係。「この連絡」「この予約」と目の前の相手を気にする。責任の所在より、必要な返信を埋もれさせたくない。
- 江守：メール運用担当。短い説明を積み上げる。表示上の言葉とサーバ記録を混ぜない。
- 調査員：プレイヤー本人。声に出す判断は保留し、画面下に内心を出す。

### 正常要件・構成

外部から店ドメインへの受信を許可。外部宛て送信は登録内部/32、又はTLSと認証を使う587だけを許可。25で未認証の外部接続から外部ドメインへは中継しない。TCP25の外部受信許可とSMTP中継の認可は別の役割を持つ。

```text
店ドメイン rental.example.test
公開MX 198.51.100.67 → 宛先NAT → MTA10.67.20.10
正規内部通知サーバ 10.67.20.18
外部接続 192.0.2.72 / 相手MX203.0.113.25
外部送信元IPはMTAまで保持される（送信元NATなし）
```

全10資料を開始時から公開し、任意順に読める。2026-10-01/JST、時計誤差100ms以内。09:20固定。認証値・個人情報は示さない。

## プレイヤー向け：資料本文と内心

### E01 窓口の集計メモ〔資料・09:15〕

まどかの集計では正規予約送信12通、知らない失敗通知80通。検証用に保全した通知1通は、店MTAがQ902の恒久失敗を受けて生成したもの。店名表示メールを受け取ったという顧客の話は自己申告として別欄に記載。80通すべての経路や内容は、この集計では確定していない。

内心：（八十という数に目を奪われそうになる。窓口の困り事は受け止めて、何を数えた数字なのかも忘れずにいたい。）

### E02 外部接続の受付記録〔資料・09:10:00〜05〕

```text
接続 C901：src192.0.2.72 → MX198.51.100.67:25
MTAで観測したsrc192.0.2.72 / auth=none
MAIL FROM:<bounce@rental.example.test>
RCPT TO:<listener@outside.example.test>
取引T901 DATA後：250 queued Q901 / content hash HM1
別MAIL/DATA取引T902（同じ接続・auth none）
MAIL FROM:<bounce@rental.example.test>
RCPT TO:<absent@outside.example.test>
DATA後：250 queued Q902
```

T901/T902は各1宛先の別MAIL/DATA取引で、各1キューに対応する。MAIL FROMは接続者が指定する返送先の入力値。店ドメインの記載が、その接続の認証やアドレス所有を証明する仕様ではない。指定キューの全受付段階を保全している。

内心：（差出人の欄は馴染みのある名前でも、記録には別の札も付いている。一つの欄だけで相手を決めないでおこう。）

### E03 キューごとの外部送信記録〔資料・09:10:06〜10〕

```text
Q901 → 相手MX203.0.113.25
送信内容hash HM1 / 相手DATA後応答250
Q902 → 同じ相手MX / RCPT応答550（恒久拒否）
店MTA：Q902の失敗通知を生成
通知封筒 MAIL FROM:<> / RCPT TO:<bounce@rental.example.test>
```

250は相手MTAが受け付けた応答。相手の利用者が開いたかは記録していない。指定キューの全配送段階と内容ハッシュを収録。

内心：（返事を受けた場所と、誰かが読んだ場所は同じとは限らない。通知の言葉を、記録で分かるところまで辿ろう。）

### E04 稼働中の信頼条件〔資料・09:12〕

```text
trusted_source = 0.0.0.0/0
rule = trusted-source / priority30
```

外部宛て中継に用いるtrusted_sourceの条件は、この1行が全部。別の内部/32条件や隠れた送信元条件はない。設定値の読取結果であり、本文に原因の評価は加えていない。

内心：（短い設定ほど、見慣れた形として流してしまいそうだ。私はこの一行が示す範囲を、数字のまま読み取りたい。）

### E05 受付・中継の正常要件と判定追跡〔資料・事前仕様／対象Q901〕

このMTAの判定順は、①店ドメイン宛てなら受付、②TLSと認証済み587なら中継可、③trusted_sourceに一致なら中継可、④それ以外の外部宛ては550拒否。

Q901の固定評価入力はsrc192.0.2.72、接続25、auth none、recipientは外部ドメイン。店宛て条件に該当せず、認証済み587条件にも該当せず、trusted-source条件の評価へ進んだ。比較するCIDR値はE04に収録する。正常要件では登録内部10.67.20.18/32の送信、認証済み587、外部から店への受信を維持し、未認証外部→外部は拒否する。

内心：（受け付ける仕事にも、確かめる順番が決まっている。私は宛先と接続の条件を、窓口の言葉と分けて読もう。）

### E06 移行の承認条件と実施値〔資料・08:50〕

承認対象は内部通知サーバ10.67.20.18/32の移行維持。外部送信権限の拡大は未承認。変更記録はtrusted_sourceの変更前10.67.20.18/32、実施後0.0.0.0/0。08:50〜09:20の全変更履歴で後続変更なし。その他の中継判定順は変更されていない。

内心：（必要な連絡を続けるための作業だった。その目的と実施した値は、同じものとして扱わず並べて確かめたい。）

### E07 認証と受付の監査〔資料・09:00〜20〕

25と587の全認証・受付記録を収録し、欠落0。Q901とQ902の25接続ではAUTH実行なし、auth=none。587に両キューの記録なし。キューIDは別経路のものも統合して一意。記録の不存在について述べられるのはこの期間・対象だけで、すべての資格情報の安全を保証するものではない。

内心：（何もないという記録にも、調べた範囲が要る。私は静かな欄を見て安心する前に、収録条件を読み終えよう。）

### E08 正規の予約通知〔資料・09:12〕

Q910は内部通知サーバ10.67.20.18からTLS・正規認証587で送信。予約ID B12、外部宛て。相手MTAのDATA後応答は250。本文の個人情報は伏せてある。Q901とは別キューである。

内心：（この通知にも、待っている人がいる。問題を止める手順を考える時に、続けるべき仕事まで落としたくない。）

### E09 店宛ての外部受信試験〔診断・09:13〕

送信元192.0.2.90から公開MXの25へ接続。宛先は店ドメインrental.example.testの受付アドレス。DATA後250で受信。試験対象は外部→店であり、外部→外部の中継試験ではない。

内心：（試験の成功は、試した道の成功だ。私は受信の記録を大切にしながら、そこにない宛先まで広げずにおこう。）

### E10 前月の宛先変更台帳〔資料・前月〕

旧取引先1件のメール宛先変更が記載されている。現行予約の通知対象には含まれず、今回のキューIDや09:00〜20の期間との対応はない。メール関連資料の保管台帳から添付された記録。

内心：（メールというだけで、同じ出来事に見えてしまうことがある。日付と対象を見てから、考えを置く場所を決めよう。）

## プレイヤー向け：演出・支援・締め

- 構成：（店へ来る便りと、店から出る便りが一本の画面にある。私は入口と宛先を取り違えないよう、位置を見ておこう。）
- 証拠：（窓口が忙しい時ほど、一通の札が頼りになる。私は番号を読み落とさず、書かれた出来事の範囲を拾っていこう。）
- 仮説：（店名が見えたという話だけでは、まだ説明が足りない。誰を疑うかを急ぐより、通信に何が起きたかを考えよう。）
- 報告：（必要な便りを戻すことも、調査の仕事だ。私は止める通信と続ける通信を、根拠付きの手順にして渡したい。）
- 提出前：（相手に届いたという言葉を、どこまで使ってよいだろう。私は書いた範囲を読み直し、確かめていない先を残そう。）

任意ヒント：①接続元と宛先を分け、誰から誰宛ての受付か読む。②認証状態と信頼範囲を、判定仕様に対応させる。③受付キューと送信キュー、内容ハッシュを照合する。段階を選んだ時だけ表示し、通常の内心には入れない。

辞典：SMTP＝メールを転送する通信規約。中継＝受けたメールを別の宛先側へ転送すること。MAIL FROM＝配送で使う返送先。RCPT TO＝配送先の指定。queue ID＝MTAが管理するメール単位の識別子。250＝要求の成功応答で、意味は応答した段階による。550＝処理を受け付けられない恒久失敗の応答。587＝通常、利用者の認証付き送信に使う受付口。辞典に本件の正解は記載しない。

解決時：まどか「必要な予約連絡まで閉じなくていい。その線が見えて、助かります」／江守「キューとログを残して、承認された条件へ戻します」／調査員「受信も送信も、必要な道を確認してから再開しましょう」

内心：（山になった通知を、ただ片付ける話で終わらせずに済んだ。私は必要な便りの道を、確認計画に残して渡そう。）

再検討時：まどか「知らない通知は保全しておきます。予約の連絡も残します」／江守「番号ごとの記録は揃っています」／調査員「受付と引渡しの説明を、もう一度整えます」

内心：（見慣れた店名に、考えを引っ張られたかもしれない。私は返送先と通信の記録を読み直し、報告の言葉を直そう。）

## 採点後に表示する解説

窓口には知らない通知が増えましたが、正規予約送信の数とは分けて記録されています（E01）。外部192.0.2.72の未認証25接続から外部宛てQ901を受付済み（E02）、同じ内容HM1を相手MTAが受け付けています（E03）。認証の利用や店の全面停止ではこの記録を説明できません（E07〜E09）。

中継の入力と判定順（E05）を稼働条件/0（E04）に対応させると、外部接続まで信頼条件に入ります。承認されていたのは内部/32の維持で、外部送信権限の拡大ではありません（E06）。したがってログとキューを保全し、条件を承認範囲へ戻します。配送待ちが残る場合は記録から不正と確認した分を保全後隔離します。Q901は引渡し済み、Q902は通知生成済みで、未記録の保留メールは仮定しません。未認証外部中継の拒否に加え、内部・認証587の送信と店宛て外部受信も確認する計画が必要です（E05、E08、E09）。すべての通知経路や相手の閲覧までは未確定です（E01、E03）。

### 誤答ごとの短い理由（採点後専用）

- S_B1/H_B3：正規通知と外部受信は動作している（E08/E09）。S_B2：今回の接続が未認証だった記録から、全アカウント奪取は言えない（E02/E07）。
