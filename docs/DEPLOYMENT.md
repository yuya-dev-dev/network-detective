# HTTPS配信と実機確認

第1事件の本番ビルドは `dist/` 全体を静的なHTTPS配信先へ配置する。ルート・サブディレクトリの両方に対応する。localStorageの保存先は配信元のscheme・host・portで決まり、これらが変わると別の保存先になる。同じoriginのパス・ハッシュ違いでは保存先を共有する。

## GitHub Pagesを使う場合

非公開リポジトリは維持する。非公開リポジトリからPagesを配信するには対応した既存のGitHubプランが必要。ソースが非公開でも、通常のPagesサイトは公開される。対応プランがない場合は、別の利用可能な静的HTTPS配信先を使う。

1. リポジトリのSettings → PagesでSourceをGitHub Actionsにする。
2. `.github/workflows/deploy-pages.yml` をデフォルトブランチへ反映する。
3. Actionsの「Deploy game to GitHub Pages」を手動実行し、配信するブランチを選ぶ。
4. 成功したdeployジョブのURLを開く。タイトル画像の表示と事件一覧の「オフライン準備完了」を確認する。

ワークフローは手動実行のみ。pushやPRでは公開しない。単体テスト・データ検証・型確認・ビルドが成功した後、`dist/` だけをアップロードする。README、設計書、レビュー、テスト、画面サンプルは配信資産に含めない。フロントエンドの配信JavaScriptには採点用データが含まれるため、解答の秘匿は提供しない。

任意の静的ホストを使う場合は、`index.html` と `sw.js` が再検証されるキャッシュ設定を推奨する。GitHub Pagesではホスト側のキャッシュ設定に従う。このワークフローは最新の `dist/` だけを配信し、独自のキャッシュヘッダー設定や旧ハッシュ資産の追加保管は行わない。キャッシュ完了済みの旧アプリは既存のService Workerキャッシュを使う。初回キャッシュと更新は実配信で確認する。GitHub Pages以外でも `dist/` のディレクトリ構成を保つ。

## 実機で残る確認

iPhone SafariとAndroid Chromeそれぞれで、端末・OS・ブラウザのバージョン、配信URL、対象コミットを記録する。クラウド実機を使う場合も、エミュレーターではなく物理端末であることを確認する。途中の報告・結果の画像をプレイヤー向けの共有へ載せない。

- タイトル→一覧→依頼→構成／証拠／仮説／報告→確認→結果→再挑戦を通して操作する。
- 全8証拠を任意順で開き、仮説と証拠の関連付け、辞典・3段階ヒント、報告の選択肢が操作できることを確認する。
- 幅360〜430px相当で横はみ出し・文字の切れ・セーフエリアとの重なりがないことを確認する。構成図の全体表示・拡大・機器詳細も確認する。
- 下書きを作り、タブ移動、ブラウザの戻る、再読み込み、ブラウザの再起動で内容が残ることを確認する。拡大・機器詳細・報告確認を開いたまま戻っても操作できることを確認する。
- 初回キャッシュ完了後に通信を切り、再読み込みから結果まで遊ぶ。再接続後の更新は、調査中に強制適用されず一覧で保存後に適用できることを確認する。
- キャッシュのない初回起動でネットワークの取得記録を取り、初回必須資産の圧縮転送量を合計する。ブラウザの転送量とローカルのgzip計算値を混同しない。

## 現在の状態

Sitesの所有者限定サイト「通信捜査室」を登録し、`.openai/hosting.json` に固定IDと静的配信対象 `dist` を保存した。サイトは未公開、ソース・配信アーカイブの送信も未実施。公式Sitesワークフローによるソース送信は自動承認レビューが、非公開ソースをSitesへ送る具体的な承認がないという理由で実行前に拒否した。許可された後に同じサイトIDを再利用し、ソース保存・アーカイブ作成・非公開配信を進める。登録済みであることを配信成功とは扱わない。

2026-10-05時点でリポジトリは非公開、Pages GET APIは404、公開URLは未設定。Pages作成APIは現在のプランがこのリポジトリに対応しないというHTTP 422を返し、サイトは作成されなかった。リポジトリの公開化や新規契約は行っていない。ワークフローは公開準備であり、実際の配信成功や実機確認の証跡ではない。物理端末の全工程操作・オフライン操作・HTTPS配信での実機転送量測定が済むまで、MVPの完成条件を満たしたとは扱わない。
