## P2-TIME：全範囲監査と途中のobservedAtの意味を揃える

**対象：全稿の正常前提、技術引継ぎの証拠時刻、完成稿の全期間監査カード、implementation-handoffのobservedAt説明。** 明確な例はSEC01 E03/E08、SEC02 E04/E08、SEC03 E06/E08、SEC04 E07、SEC05 E03/E04。全件監査・全展開台帳と書くSEC04 E03/E05も同じ基準で整理する。

SEC04 E07は18:00〜18:45のフォーム・更新・出荷の完全範囲を示すが、observedAtは18:24。取得18:45だけでは、18:24時点の状態資料へ後の完全範囲を付記したのか、18:45まで観測した集計資料なのか決まらない。SEC01 E03は10:12に対し10:13の同意と10:30までの全件性を含む。SEC03 E06も12:21のobservedAtに最終受信12:22を含む。この曖昧さは「記録がない」ことを反証に使う稿で特に目立つ。

**最小修正：全期間の集計・全件性を示すカードのobservedAtを、その収録終端又は集計を確定したsnapshot時刻へ揃える。元イベント時刻は本文に残す。** 複数イベントを一枚へまとめる資料は最後のイベント時刻以後の観測とする。通常の一件ログ、設定、試験まで一律にsnapshotへ変えない。各稿に「observedAtはこの資料の状態・範囲を観測した時刻。全件資料は収録終端、複数イベント資料は最後のイベント以後。個別イベントの時刻は本文に記載。取得は資料を調査へ揃えた時刻」と短く定義する。SEC03 E06は少なくとも12:22以後の配送確認時刻が必要。

別案として焦点イベント時刻の意味を公開定義し、全範囲の確定時刻を本文へ別記する方法も成立する。ただしSEC04 E07の18:24は記載された焦点イベントと対応していないため、全範囲資料の時刻を揃える方が変更量と解釈負担を抑えられる。

**採点影響：なし。** EID、ログ内時刻、因果、範囲、満点集合は維持する。全件性の意味をプレイヤーが同じ基準で読めるようにする修正。

## 成立を確認した点

- SEC01：本人ログイン・同意・外部API利用をgrantで結ぶ。正常要件を既知とするC_POLICYのE04/E06一枚代替は成立。C_SCOPEでは保有件数と送信完了と期間全要求を区別するため、E02+E05を満点としない理由がある。即時access拒否とpassword変更の独立性は製品固有前提として公開されている。
- SEC02：明示Lax、別site、host-only、トップレベルGET、iframe/imgとの区別が揃う。外部サーバからCookie付き要求を直接APPへ送る図になっていない。TLS終端後のHTTP/8080も完成稿で正しく分離された。ownerとenumが正常でも意思確認を欠く変更が通る。C_EFFECTのE03+E04又はE04+E06は同じ要求を異なる観測点で結ぶ妥当な代替。
- SEC03：clear-signingと内容暗号化を分け、共通鍵・受信者鍵・署名者鍵・CA鍵の役割は混同していない。区間TLS成功とrelay保管時の内容秘匿を区別する。C_SIGN/C_GAPは形式/設定と公知要件で一枚立証が成立する。索引生成から人物閲覧や外部公開を断定しない。
- SEC04：E04はDL74受入物のdigestと添付provenanceを対応させた控えになっており、E02+E04は正式に代替として成立する。受入、展開、EX74、Q74、I74の関連付けをPIDだけに依存しない。既知advisoryの対象版外と実行計測でH_DRAWを排除できる。広いservice権限は既存条件で、今回の異常を起こした実体差と区別されている。
- SEC05：E03/E07の一枚代替は時刻・source・ID・node・失敗・重複排除を満たす。E09の39行は13password試行×3段階で、MFA成功10件は別監査と明記され、加算の矛盾は解消している。値がないpasswordを同一と断定せず、通知生成0と配送停止を分ける。以前や他経路まで侵害不存在を広げない。

全候補のfeedbackと正答・誤答・criticalの結論に、上記SEC05の説明以外の不一致は見つからなかった。100点10/30/30/10/10/10、主張3枚・各1〜2証拠、OR/AND、部分点5、誤主張/無関係のみ0、非矛盾の余分な一枚を含む満点10、criticalで解決不可という契約を維持している。正常対照を矛盾へ分類していない。

## 技術一次資料との照合

今回あらためて該当箇所を参照した。研究メモのIPA10題・45ページの再読や最新版シラバス確認を、田中自身が今回実施したとは記録しない。その記録は主担当・作家の研究報告として読んだ。

- OAuth失効は連鎖ポリシーや実装の伝播差を伴うため、SEC01の即時API拒否を架空製品前提と区別する記述は妥当。[RFC7009 §2.1](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1)
- 明示Laxのcross-siteトップレベルsafe-method遷移とHttpOnlyの役割はSEC02の観測に一致する。[MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
- 状態変更GETを避け、server側でtokenを検証する方向は妥当。tokenだけで人間の内的意思を証明する一般保証ではなく、本件の確認フォーム仕様として読む。[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- multipart/signedはclear-signingであり、署名付き内容の秘匿を意味しない。SEC03の形式比較は妥当。[RFC8551 §3.5.3](https://www.rfc-editor.org/rfc/rfc8551.html#section-3.5.3)
- artifact/subject対応と信頼するbuilder署名に加え、期待するビルド条件を照合する方向はSEC04と整合する。SLSA完全準拠と称する必要はない。[SLSA1.2 Verifying artifacts](https://slsa.dev/spec/v1.2/verifying-artifacts)
- account lock、複数IDへ試す活動、MFAを分ける方向は妥当。SEC05の8ID/5分は独自の通知要件であり、一般標準値ではない。[OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
